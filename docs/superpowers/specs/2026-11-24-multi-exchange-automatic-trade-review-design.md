# WaveKB 多交易所自动交易复盘设计

日期：2026-11-24
状态：待确认

## 1. 意图

把 WaveKB 的交易工作台升级为多交易所、多账户统一复盘系统。一个用户可以同时绑定 Binance、OKX、Bybit、Bitget 和 Exness 的只读 API，工作台默认展示合并总览，并允许按平台和具体账户筛选。

首版只处理可以形成明确开平仓生命周期的衍生品：Binance U 本位合约、OKX USDT 永续/交割合约、Bybit USDT 线性合约、Bitget USDT 合约，以及 Exness API 账户中的外汇、贵金属、指数、能源和加密货币 CFD。首版不处理现货。

系统自动同步账户权益、成交、已实现盈亏、手续费、资金费或隔夜费、分红和外部资金流，映射为统一数据模型，再生成账户概览、交易统计和单笔复盘。单笔复盘继续只保留三个主要主观输入：交易理由、是否遵守计划、下次改进。AI 只在用户主动触发时结合选定的 WaveKB 书籍知识库生成带来源的复盘建议。

## 2. 用户已经确定的产品决策

- 同时支持 Binance、OKX、Bybit、Bitget 和 Exness。
- 一个用户可以同时绑定多个平台和多个账户。
- 工作台默认显示所有已选账户的合并总览，同时提供平台和账户筛选。
- 加密交易所首版只做 USDT 本位合约；Exness 首版做 API 账户支持的 CFD 品种。
- 首版不做现货。
- 使用“统一数据模型 + 交易所适配器”方案，不为每家复制一套工作台和统计代码。
- 不接入返佣、合作伙伴报表、客户业绩、订阅或自动下单功能。

## 3. 当前状态与外部约束

- 现有 WaveKB 只有一个 Binance U 本位连接，网关保存 AES-256-GCM 密文，浏览器只获取末四位和非敏感状态。
- 现有同步只获取账户权益、钱包余额、未实现盈亏和外部净资金流，没有成交明细，因此不能生成真实单笔复盘。
- 现有服务默认取用户最近一个未禁用连接，必须改为按用户列出和同步多个连接。
- 现有 `/workbench` 仍以 11 步 `workbench_analyses` 和私人记录为主；新工作台替换默认入口，但旧分析保持只读、私人记录继续可用。
- Binance、OKX 和 Bitget 的首版历史回补上限按最近 90 天处理。Bybit 虽有更长的部分账户流水能力，首版也使用共同的 90 天产品上限，避免同一合并统计中出现不可解释的覆盖差异。
- Exness 的成交历史范围不能硬编码；适配器必须先读取账户 limits 中 `getDealsHistory` 的 `history_age_days` 和 `history_range_days`，再决定可回补起点和窗口。
- Exness 历史 deal 自带 `position_id`，同一品种可能同时存在多笔独立持仓；不能套用加密合约“品种净仓从零到零”的唯一归组方式。
- 各平台的账户币种、结算币种、手续费符号、资金费符号、成交排序和游标规则不同。适配器负责解释原生语义，统一层不得猜测。

## 4. 目标

1. 一个账号可安全保存多个平台、多个账户的只读连接。
2. 打开 `/workbench` 即看到合并复盘，无需创建 11 步分析。
3. 可按“全部平台 / 单个平台 / 单个账户”筛选所有指标、图表、日历和交易列表。
4. 每个适配器把原生数据转换为同一组账户快照、成交、资金事件和交易周期契约。
5. 自动展示当前权益、累计盈利、时间加权收益率、已实现净盈亏、最大回撤、胜率、盈亏比、费用和品种归因。
6. 任何跨币种合并数值都保留原币种、换算来源和时间；无法可靠换算时不进入总计并明确提示。
7. 单笔交易使用一个页面完成查看和极简复盘。
8. AI 使用统一交易周期契约，不需要知道具体交易所私有字段。
9. 移动端和 iOS PWA 可完成连接管理、筛选、查看、编辑和 AI 请求。

## 5. 非目标

- 不提供任何交易、改单、撤单、平仓、跟单、EA 控制或自动化策略执行功能。
- 不请求 Exness Trading Full access、Partnership 或 Transfers 权限。
- 不请求其他交易所的交易和提现权限。
- 不处理现货成本基础、链上钱包、期权、币本位合约或组合保证金的复杂资产归因。
- 不导入 Exness 客户业绩、返佣、合作伙伴、推广或奖励数据。
- 不把用户的成交、仓位、账户、资金流水或复盘内容公开。
- 不把 USDT、USD、EUR 等资产在没有来源和时间戳的情况下直接视为相同价值。
- 不复制参考网站或交易所客户端的代码、品牌、文案或视觉。

## 6. 反目标

出现以下任一情况即视为失败：

- 五个平台各自拥有不一致的胜率、净盈亏或周期口径。
- 同一成交因重试、游标重叠或 WebSocket 重连被重复计算。
- 一个账户的 API 密钥可以被浏览器读取，或被服务端用于任何写交易操作。
- Exness 的 `position_id` 被错误合并，导致同时存在的独立持仓互相抵消。
- 资金费、swap、分红、手续费、转入转出被错误归类为交易盈利。
- 多账户合计隐藏未换算资产或覆盖缺口，给出看似精确但实际不完整的总额。
- 排行榜利用不同历史覆盖长度制造不可比收益。
- 为了切换工作台而删除旧分析、私人记录或历史连接数据。

## 7. 已考虑的实现方案

### 方案 A：每家交易所独立实现

每个平台建立自己的表、同步服务和页面。初期接口简单，但五套统计口径会快速分叉，修复一次周期算法需要重复修改，无法可靠合并账户。

### 方案 B：统一数据模型 + 交易所适配器（已选）

每个平台只负责鉴权、能力发现、分页、错误转换和原生字段归一化。统一层负责幂等存储、周期重建、指标、页面和 AI。平台特性通过能力声明和明确的策略接口表达，不通过散落的条件判断表达。

### 方案 C：保存全部原始响应后离线计算

审计最完整，但会扩大敏感数据、数据量和泄漏面，还会把供应商响应变化直接传播到内部系统。首版不采用；只保存必要的原生 ID、归一化数据和不含正文的同步审计摘要。

选择方案 B，因为它最符合同时绑定多平台、多账户和统一复盘的目标，也能将供应商变化隔离在各自适配器中。

## 8. 统一适配器架构

### 8.1 适配器接口

所有平台实现同一个服务端接口：

```ts
type TradingProvider = "binance" | "okx" | "bybit" | "bitget" | "exness";

interface TradingProviderAdapter {
  readonly provider: TradingProvider;
  validateCredentials(input: ProviderCredentialInput): Promise<ValidatedAccount[]>;
  discoverCapabilities(account: ProviderAccount): Promise<ProviderCapabilities>;
  fetchAccountSnapshot(account: ProviderAccount): Promise<CanonicalAccountSnapshot>;
  fetchHistory(account: ProviderAccount, cursor: ProviderCursor): Promise<ProviderHistoryPage>;
  normalizeHistory(page: ProviderHistoryPage): CanonicalHistoryBatch;
}
```

适配器不得暴露下单方法。公共注册表只接受上述读取接口；任何带交易动词的客户端方法不得进入该接口或依赖注入容器。

### 8.2 平台能力声明

`ProviderCapabilities` 至少包含：

- 支持的产品类别和账户模式。
- 历史最大年龄、单次时间窗口、分页方式和最大页大小。
- 是否提供 position ID、已实现盈亏、手续费币种、资金费/swap、外部资金流和账户美元估值。
- 支持的持仓归组策略：`net_zero_cycle`、`hedge_zero_cycle` 或 `position_id_cycle`。
- 账户币种、结算币种和可用估值路径。

能力在每次首次绑定和必要的重新发现时保存快照。供应商改变限制后，新同步使用新能力，不回写伪造旧历史。

### 8.3 平台实现

- Binance：USD-M Futures；HMAC-SHA256；成交和 income 历史；`BOTH/LONG/SHORT` 零仓周期。
- OKX：`SWAP`/`FUTURES` 且 USDT 结算；HMAC-SHA256 + API passphrase；fills history、bills 和账户余额；`net/long/short` 周期。
- Bybit：`linear` 且 USDT 结算；V5 签名；execution、transaction log 和 wallet balance；`one-way/hedge` 周期。
- Bitget：`USDT-FUTURES`；HMAC-SHA256 + passphrase；fills、account bills 和账户资产；按账户模式重建周期。
- Exness：Trading Read-only；Ed25519 `EXN-*` 签名、Account ID 和 access-point discovery；deals、orders、snapshot、limits；按 `position_id` 建立周期。

## 9. 统一数据模型

### 9.1 连接与凭据

凭据与交易账户分开建模：

- `exchange_credential_sets` 代表一组加密 API 凭据和供应商，密钥材料只保存一次。
- `exchange_connections` 代表一个实际交易账户，并通过 `credential_set_id` 引用凭据。
- 一个凭据集可以连接多个官方允许的账户；Exness Read-only key 最多可发现 1–10 个账户，用户在验证后明确选择要接入的账户。
- 删除一个交易账户不会删除仍被其他连接使用的凭据；最后一个连接断开后凭据集立即停用并按删除策略清理。
- 轮换凭据以凭据集为单位执行，所有引用账户进入“待重新验证”，成功后再恢复同步。

扩展 `exchange_connections`：

- `provider`、`external_account_id_hash`、`account_label`、`account_currency`。
- `capabilities`、`history_coverage_started_at`、`equity_tracking_started_at`。
- `sync_status`、`last_synced_at`、`last_error_code`、`lease_until`。
- `public_enabled` 继续是逐连接明确同意，不因新增连接自动公开。

`exchange_credential_secrets` 使用统一加密 envelope 保存供应商所需字段：

- Binance：API Key、Secret。
- OKX/Bitget：API Key、Secret、Passphrase。
- Bybit：API Key、Secret。
- Exness：API Key、Ed25519 私钥或 Exness 生成的 Secret、允许的 Account ID、discovery host 必要信息。

浏览器永远只收到供应商、账户标签、脱敏标识、权限验证结果和同步状态。

### 9.2 `CanonicalAccountSnapshot`

- connection/provider/account identity。
- captured time。
- account currency。
- equity、wallet balance、unrealized PnL 原币值。
- USD/USDT 估值、估值汇率、估值来源、估值时间和 `valuation_status`。

### 9.3 `CanonicalFill`

- 供应商和连接 ID、原生成交 ID、订单 ID、可选 position ID。
- 标准化品种、原生品种、产品类别。
- 买卖方向、持仓方向、开/平语义。
- 成交价、数量、合约乘数、成交时间。
- 已实现盈亏原币值、手续费原币值与资产、maker/taker。
- 归一化 USDT/USD 数值只有在可靠换算存在时填写。

### 9.4 `CanonicalCashEvent`

标准类型：`deposit`、`withdrawal`、`internal_transfer`、`funding`、`swap_fee`、`commission_adjustment`、`dividend`、`admin_adjustment`、`bonus`、`unknown`。

每个事件保存原始类型代码、金额、资产、时间和可选品种/position ID。外部资金流用于收益率调整，不计入交易盈利；无法确定的类型保留为 `unknown` 并排除出正式指标。

### 9.5 `CanonicalTradeCycle`

- 加密合约：同一连接、品种和持仓方向从零仓开始到再次归零结束；反手穿越零仓拆成两个周期。
- Exness：优先按 `position_id` 聚合 open/close deal；部分平仓保留在同一周期，完全关闭后结束。
- 每个周期保存稳定键、提供商、连接、账户币种、开平仓均价、数量/合约、起止时间、已实现盈亏、手续费、资金费/swap、净盈亏和完整性状态。
- 周期拥有永久内部 UUID 和可变的供应商事实版本。Exness 等有原生 position ID 的平台以连接 + position ID 建立身份；没有原生 position ID 的平台使用连接 + 周期锚点填充集合，并通过 lineage 表维护重建前后的身份，不把可变化的最早开仓成交 ID 直接当数据库主键。重建使用 upsert，不全表删除。

### 9.6 用户复盘

`trading_trade_reviews` 与周期稳定 ID 一对一。浏览器只能通过窄 RPC 更新：

- 交易理由。
- 计划遵守情况：未选择 / 是 / 部分 / 否。
- 下次改进。
- 少量自定义标签。
- 可选的计划止损价或计划风险金额。

R 倍数只在计划风险和净盈亏可使用同一可靠币种时计算。

## 10. 历史同步与幂等发布

### 10.1 首次回补

- 产品首版最多请求最近 90 天。
- 如果供应商只允许更短时间，以供应商返回的能力为准。
- Exness 先读取 limits，再把 90 天产品上限切成允许的 `history_range_days` 窗口。
- 每个连接独立显示“交易历史覆盖起点”和“权益跟踪起点”。
- 回补起点处已有净持仓但没有开仓证据时，第一段标记为 `incomplete_opening_history`，直到首次归零前不进入周期指标。

### 10.2 增量同步

- 默认沿用 15 分钟定时任务，手动刷新受节流控制。
- 每个连接有独立租约、供应商游标和最后已发布 generation。
- 时间游标保留受控重叠区间，再按供应商原生 ID 幂等去重。
- 供应商 opaque cursor 原样保存，不解析、不构造。
- WebSocket 仅可作为未来的低延迟增强，不能作为唯一历史来源；断线后必须用 REST 历史对账。

### 10.3 原子发布

远端拉取、分页和归一化可以分阶段执行；数据库通过一个批次 RPC 在同一事务中：

1. 校验连接所有权与 generation。
2. upsert 快照、成交和资金事件。
3. upsert 稳定交易周期并标记被替代版本。
4. 更新覆盖范围、游标和最后同步状态。
5. 提交新 generation。

任一步失败都不推进已发布游标，页面继续读取上一次完整 generation。

### 10.4 迟到成交与周期 lineage

- 每次重建保存周期 revision 和组成成交 ID 的确定性摘要。
- 周期只发生时间延伸且仍包含原锚点成交时保留内部 UUID，只增加 revision。
- 一个周期拆分时，包含原锚点的片段保留 UUID，其余片段获得新 UUID。
- 多个周期合并时，最早创建的 UUID 成为 canonical，其他 UUID 写入 alias/lineage，不丢失引用。
- 如果被合并的多个周期都已有用户复盘，不自动拼接或覆盖文字；非 canonical 复盘标记为 `needs_reconciliation`，在页面并列展示供用户处理。
- AI 输出绑定生成时的 cycle revision。事实变化后保留旧结果但标记“交易数据已更新，需要重新分析”。

### 10.5 重复绑定与重连

- 同一 WaveKB 用户再次绑定相同供应商和外部账户时复用原 connection，替换/轮换凭据并续接历史，不创建第二份统计。
- 已断开但未删除历史的账户重连时恢复原 connection ID。
- 不同 WaveKB 用户不能同时绑定同一个外部交易账户，避免排行榜和聚合重复；返回通用的“账户不可用”错误，不向第二个用户泄露已绑定者身份。
- `external_account_id_hash` 使用服务端稳定密钥生成的 HMAC，数据库对 provider + hash 建立唯一约束；浏览器永远看不到完整账户 ID 或全局哈希。

## 11. 多账户合并与币种换算

### 11.1 原币值优先

每个连接的详情始终展示账户原币值。所有换算金额旁都可查看：原金额、换算资产、汇率、来源和时间。

### 11.2 估值规则

- USD 账户直接使用 1。
- USDT 账户以 1 USD 近似展示，但标记“USDT 近似美元”，并保留稳定币差异提示。
- 其他账户币种优先使用同一供应商官方市场数据中与 USD/USDT 的直接或可验证反向报价。
- 需要三角换算时只允许一个受控中间资产，并保存两段报价来源。
- 缺少报价、报价过期或路径不唯一时，`valuation_status` 为 `unavailable`，该连接不进入跨账户金额总计。

### 11.3 合并指标

- 当前总权益：所有可估值连接最新快照的 USD 估值之和，并显示未纳入连接数量。
- 累计盈利：选定范围结束权益减去范围开始权益和范围内净外部资金流；连接在范围中途开始跟踪时以第一份快照为该连接基准。未实现盈亏通过权益变化进入累计盈利，但不进入“已实现净盈亏”。
- 合并 TWR：以 15 分钟 UTC 网格使用每个连接最近有效快照与该区间外部资金流计算；快照超过 35 分钟即视为缺口，显示“不完整”，不跨缺口插值。
- 最大回撤：只基于可估值的合并权益时间序列。
- 胜率、盈亏比和交易次数：可跨账户直接按完整周期聚合，但金额型值只使用可靠换算的周期。

页面必须同时展示“已纳入 X 个账户”和“Y 个账户因换算/覆盖不足未纳入金额总计”。

### 11.4 唯一会计口径

六个首屏指标固定为：当前权益、累计盈利、TWR、最大回撤、已实现净盈亏、胜率。

- 已实现净盈亏 = 已实现交易盈亏 − 交易手续费 + 已归属资金费/swap + 已归属持仓分红。bonus、admin adjustment、充值、提现和内部转账不属于交易盈亏。
- 未闭合周期不进入胜率、平均盈利、平均亏损或 Profit Factor，但它的未实现盈亏通过账户快照进入权益和累计盈利。
- “盈亏比”明确拆成平均盈利 ÷ 平均亏损绝对值与 Profit Factor（总盈利 ÷ 总亏损绝对值）两个数字，不用一个含糊字段代替。
- 同一合并筛选范围内可确定为两个已选账户之间的内部转账，在组合层抵消；只选中一端时作为该连接外部资金流。无法配对的转账标记未分类并使相关组合收益显示不完整。

### 11.5 权益与汇率历史边界

- 交易成交最多回补 90 天；权益快照、历史估值率、TWR、累计盈利曲线和最大回撤只从 WaveKB 开始跟踪后产生，不从成交倒推绑定前权益。
- 每次账户快照同时保存当时使用的汇率和估值路径。历史指标使用历史快照中的汇率，不用当前价格重算过去权益。
- 首版不建设独立的历史 FX 回补管线；缺失的绑定前权益和汇率明确显示不可用。

## 12. 工作台体验

### 12.1 连接管理

工作台顶部提供“管理交易账户”，显示五个平台入口和已有连接列表。每个连接显示：

- 平台、账户标签、脱敏账户标识和账户币种。
- 权限状态：已验证只读 / 权限不安全 / 待验证。
- 最近同步、历史覆盖、权益跟踪、错误状态。
- 手动同步、重新验证、断开和是否加入公开排行。

用户创建连接时只显示该平台必要字段。界面明确引导关闭交易/提现权限和设置服务器 IP 白名单。

### 12.2 `/workbench` 合并总览

顶部筛选：

- 范围：7 天、30 天、90 天、全部可用。
- 平台：全部、Binance、OKX、Bybit、Bitget、Exness。
- 账户：根据已选平台列出。

所有日历、按日/时段归因和日期筛选均在查询时把 UTC 转换为用户选择的 IANA 时区。默认使用浏览器时区，无法取得时回退 `Asia/Shanghai`；用户改变时区后重新查询并重算分组，不永久改写历史事实。

正文顺序：

1. 同步和覆盖状态。
2. 六个核心指标。
3. 合并权益与累计净盈利曲线。
4. 交易日历。
5. 平台、账户、品种、方向、时段归因。
6. 最近交易周期列表。
7. 次级入口：私人记录、研究草稿、历史 11 步分析和 AI 模型设置。

首页不出现“新建分析”或“11 步”按钮。

### 12.3 单笔复盘

`/workbench/trades/[id]` 显示统一交易事实，并用平台标识说明数据来源。Exness 页面显示手数、position ID、swap 和账户币种；加密合约页面显示合约数量、资金费和结算币种。

三个主要主观字段、自动保存、计划风险和 AI 知识范围在所有平台保持一致。供应商特有但不影响复盘的字段放入折叠的“原始交易信息”，不把整份 API 响应暴露给浏览器。

## 13. 排行榜边界

- 连接默认私有。用户必须逐连接明确同意加入排行。
- 排行榜只接收连接级聚合收益率、当前估值和累计盈利，不读取成交、品种、仓位或复盘表。
- 多连接用户的公开成绩只合并用户明确选择且估值可用的连接。
- 排行开始时间以最早被纳入连接的公开跟踪时间为准，并显示实际覆盖。
- 不用 API 可提供的更长历史回补排名；公开收益从 WaveKB 绑定并开始记录权益快照后计算，以保持平台间可比性。

## 14. AI 与知识库

AI `trade_review` 任务只读取统一交易周期和用户自己的复盘字段，不读取供应商密钥、原始 API 响应、其他账户或排行榜数据。

输出结构：

1. 事实摘要。
2. 纪律观察，区分用户陈述和模型推断。
3. 波浪/结构假设；证据不足必须为未知。
4. 关联书籍、章节和知识单元。
5. 下次检查清单，不包含买卖指令和收益承诺。

同一 AI 任务可选择全部知识库或单独一本书。模型输出经过结构校验、知识引用校验和现有规则闸门，不覆盖用户正文和确定性指标。

## 15. 隐私与安全

- 所有连接、密钥、成交、事件、周期和复盘表启用 RLS，服务端事实写入仅限 service role。
- 每张私有事实表通过连接 + 所有者组合约束验证归属，不能只信任客户端提供的 owner ID。
- 凭据用现有主密钥加密；日志、错误、AI 输入和审计不出现密钥、签名、passphrase 或完整原始响应。
- WaveKB 只要求 Exness Trading Read-only，并明确告知用户不要授予 Trading Full access、Partnership 或 Transfers。若官方读取接口返回可验证 scope，发现额外权限时拒绝连接；若供应商不提供 scope introspection，则不能通过危险的写请求试探权限，只能要求用户明确确认并依靠服务器根本不存在写交易调用路径来限制风险。
- 其他平台同样在可以读取权限列表时拒绝交易或提现权限；无法读取时要求明确只读确认，并且适配器接口只包含读取操作。
- 供应商适配器的 HTTP allowlist 固定协议、主机和路径，不接受用户自定义 API URL；Exness access point 只能来自官方 discovery 返回并经过主机校验。
- 密钥轮换和断开立即停用旧密文；历史复盘默认保留为只读，用户可另行选择删除。
- 原始账户 ID 使用服务端加盐哈希做重复检测，浏览器只显示安全脱敏值。

### 15.1 断开、删除与保留

- “断开连接”立即停用并删除该凭据集的密钥材料（仍被其他连接引用时除外），停止同步和公开排行；规范化事实、周期、复盘和 AI 结果保留为私有只读历史。
- “删除交易数据”立即从用户界面和查询中隐藏，进入最长 30 天的硬删除队列；硬删除级联清除快照、成交、资金事件、周期、复盘和 AI 结果。
- 不含密钥、账户号、成交正文或复盘正文的最小删除审计记录保留 90 天后清理。
- 用户未主动删除时，历史数据不因 API 断开自动过期；账户级删除继续遵守 WaveKB 全站账户删除政策。

## 16. 错误处理与可观察性

- 供应商原始错误转换为固定安全代码：鉴权、权限、限速、时间偏差、账户模式、历史范围、服务不可用和解析错误。
- 单个连接失败不阻塞其他连接同步或合并页面；页面明确显示被排除的连接。
- 指标记录每个平台请求次数、分页数、延迟、限速、回补进度、批次成功/失败和最后安全错误码，不记录响应正文。
- 供应商字段发生未知枚举或破坏性变化时 fail closed：保存错误状态，不把未知数据计入指标。

## 17. 测试与验收

### 17.1 统一契约

- 五个适配器使用同一组契约测试，验证确定的输入会产生同一语义的标准化结果。
- 每个平台都有签名黄金样例、分页、时间窗口、游标、限速和错误投影测试。
- 未知字段可以忽略，未知关键枚举必须拒绝，不能静默映射。

### 17.2 周期与指标

- 单向、双向、加仓、减仓、部分平仓、反手和截断历史都有精确数值夹具。
- Exness 同品种多 position ID、部分平仓、swap、commission、balance 和 dividend 不会错误合并。
- 乱序、重复、迟到成交和批次重试保持稳定周期 ID 与相同结果。
- 资金费/swap 归属不明确、非结算币手续费和缺少汇率时严格排除并提示。
- 多账户合并、外部资金流、覆盖缺口、USDT 近似、反向报价和三角换算有精确测试。
- UTC 跨午夜和 DST 汇总有测试。

### 17.3 权限

- 当供应商公开权限元数据时，交易/提现/Full access 凭据不能通过验证；没有 introspection 的平台必须显示“权限由用户确认”，且服务器不存在任何写交易适配器方法。
- 浏览器、普通用户和其他用户无法访问密钥或跨所有者事实。
- 供应商客户端没有被工作台调用的写交易方法。
- 排行榜响应仍只有原有公开聚合字段。

### 17.4 页面

- 无连接、单连接、多连接、同步中、部分历史、部分估值、空历史、错误和正常状态都有组件测试。
- 筛选会改变所有指标和列表，不会只改变视觉标签。
- 桌面、390px 移动端、键盘操作和 PWA 安装模式可完成主要流程。
- 旧私人记录和历史分析仍可访问，默认工作台不出现新建 11 步分析入口。

## 18. 发布策略

1. 先以 additive migration 扩展凭据集、多连接、统一事实表、lineage、RLS 和 RPC。
2. 部署统一契约与 Binance 适配器，验证与现有结果一致。
3. 依次启用 OKX、Bybit、Bitget、Exness 适配器；每个适配器都可通过服务端 feature flag 独立关闭。
4. 后台回补各连接，未完成时页面只显示部分历史。
5. 新工作台在总 feature flag 后运行，旧前端和新网关在切换期双版本兼容。
6. 验证私有数据、合并指标、排行榜隔离和移动端后启用生产工作台。
7. 回滚只关闭对应 flag，不删除迁移数据或旧记录。

现有 Binance 连接不要求用户重新授权：迁移保留原 connection ID、加密 envelope、权益快照、公开排行同意和跟踪起点，并在后台创建新的 credential set 引用。首次新网关同步验证凭据并补齐外部账户哈希与 90 天成交历史；验证失败时保留旧快照和安全错误状态，不静默重置收益基线。

## 19. 实现者必须遵守的决定

- 只实现读取和复盘，不实现任何交易操作。
- 统一模型是页面、指标和 AI 的唯一数据入口；供应商原始字段不能直接渗入通用层。
- 五个平台允许同时绑定，多账户默认合并但始终可以筛选。
- 加密交易所只做 USDT 合约，Exness 做 API 账户支持的 CFD，首版不做现货。
- 跨币种金额必须有估值证据；缺失时宁可显示不完整也不伪造。
- 保留旧数据但不再推广 11 步分析。
- 排行榜与私人复盘继续使用独立数据边界。
